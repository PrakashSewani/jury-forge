# Decisions

Append-only log of settled decisions. New entries get the next number, a date, and a sentence of
context. If a decision is reversed, add a new entry that supersedes the old one — never edit
history. The agent records decisions here **before** implementing them (see `AGENTS.md`, rule 2).

## D-001: Stack selection

**Date:** 2026-10-02

**Decision:** TypeScript across the repo, npm workspaces on Node 24 (`.nvmrc`), two deployables
and one shared package — all versions resolved live from npm on this date:

- **Product** (`product/`) — one Cloudflare Worker serving the dashboard and the API:
  - TypeScript 6.0.3 — 7.0.2 is latest, but `typescript-eslint` caps at `<6.1.0`; revisit when
    tooling catches up.
  - Cloudflare Workers via `wrangler` 4.146.0, built and served by `@cloudflare/vite-plugin`
    1.62.4, Vite 8.3.2, `@vitejs/plugin-react` 6.1.1, React 19.3.0.
  - Hono 4.13.12 for routing; Zod 4.6.5 for validation.
  - GitHub: Octokit 5.0.5, `@octokit/auth-app` 8.3.1, `@octokit/webhooks` 14.2.0 (signature
    verification + payload types; the standalone `webhooks-methods`/`webhooks-types` packages
    are either covered by it or deprecated).
  - Storage: Cloudflare D1 (SQL schema via `wrangler d1 migrations`). Runs: Durable Objects
    (see D-006). Worker types generated by `wrangler types` into a committed
    `worker-configuration.d.ts` — not `@cloudflare/workers-types` (superseded, per Cloudflare's
    current TypeScript guidance).
  - Tests: Vitest 4.1.11 + `@cloudflare/vitest-plugin` 1.3.5 (the Workers Vitest integration; the
    older `@cloudflare/vitest-pool-workers` no longer exports its `./config` helper and is
    superseded by the plugin API). Vitest stays on 4.x because the plugin peers `^4.1.0`.
- **Site** (`site/`) — Astro 7.3.5 static promo site with Tailwind CSS 4.3.3, deployable
  independently as Cloudflare static assets.
- **Shared** (`shared/`) — brand constants and API contract types, consumed as TypeScript source
  (no build step).
- **Tooling** — ESLint 10.11.0 + typescript-eslint 8.71.0 + Prettier 3.9.9; one `npm run check`
  command (typecheck + lint + format:check + tests + build); GitHub Actions CI running exactly
  that on PRs to `dev`/`main` and pushes to `dev`; label-driven release workflow from `main`
  (see D-007). Deployments are manual, to the owner's own account.

**Why:** the free plan covers the whole control plane, and Durable Objects make multi-minute
review runs viable without paid-only products (D-006). One language, one toolchain, one deploy
command for the product; the promo site stays static and uncoupled.

**Rejected:** Node container on Fly.io/Railway (a server to operate; Cloudflare covers it);
Vercel/Next.js (short-lived functions cannot run review jobs); Cloudflare Agents SDK
(WebSocket/stateful-agent shaped — a plain Durable Object state machine is smaller); Cloudflare
Workflows (effectively paid-only — free tier caps step compute at 10 ms; see D-006); Drizzle ORM
(raw SQL plus `wrangler d1 migrations` is enough for this schema); `@cloudflare/workers-types`
(superseded by `wrangler types`); TypeScript 7.0.2 and Vitest 5.0.3 (ecosystem lag, noted above).

**Confirmed by the user in chat on 2026-10-02** (name, runtime, dashboard surface, execution
model, and the post-pivot shape).

## D-002: Branching and automated releases

**Date:** 2026-09-26

**Decision:** `dev` is the default integration branch. Agent changes use feature branches and
pull requests targeting `dev`; releases flow from `dev` to `main`. Release-related workflows run
only after changes merge to `main`. A release PR must carry exactly one of
`release:patch`, `release:minor`, or `release:major`; the release automation applies that bump to
the chosen stack's version source, creates a matching `v<version>` tag, and publishes a GitHub
release. A merge without a release label does not publish a release. `dev` carries unreleased
work between releases and may match `main` immediately after one. Product/site deployment remains
manual. Implemented on 2026-10-02 as `.github/workflows/release.yml` + `scripts/release.mjs`
(version source: root `package.json` / `package-lock.json` / `CHANGELOG.md`).

## D-003: Agent operating model

**Date:** 2026-09-26

**Decision:** The primary agent acts as senior architect and owns requirements analysis,
architecture, documentation, code generation, integration, testing, and final verification.
Subagents are optional and restricted to one sequential, read-only discovery or evidence-gathering

## D-004: Distribution model — self-hosted, single-tenant

**Date:** 2026-10-02

**Decision:** Jury Forge ships as a self-hosted, single-tenant deployment. Each user deploys
their own instance (Worker + D1 + their own private GitHub App) into their own Cloudflare
account; the project operates no central service and holds no user data. Default cost posture is
Cloudflare's free plan, with Workers Paid ($5/month, the owner's own account) documented as
optional headroom for CPU on very large PRs. The promo site is static and deploys separately.

**Why:** the user's directive — code, credentials, and model spend stay in the owner's account;
no platform to operate or pay for; single-tenant removes multi-tenant auth and data modeling
entirely.

**Rejected:** a shared hosted app (platform cost + custody of user credentials and code);
"install a shared app, then it provisions your worker" (a GitHub App has exactly one webhook
URL, and provisioning into someone's Cloudflare account would require a central service —
exactly what this model avoids).

## D-005: Per-instance private GitHub App via the manifest flow

**Date:** 2026-10-02

**Decision:** The setup wizard registers a **private** GitHub App owned by the user's personal
account or an organization they administer, using GitHub's App Manifest flow. The manifest
prefills the webhook URL, OAuth callback, permissions, and events from the instance's own URL
(`public: false`). Private apps are installable only on the owning account, and only the owner
(personal) or members of the owning organization can authorize them. The app's runtime-generated
credentials (app id, private key, webhook secret, client secret) and all BYOK provider keys are
encrypted with AES-256-GCM (WebCrypto) and stored in the instance's D1, with the master key held
as a Worker secret — Workers secrets cannot be written at runtime, so runtime-created credentials
must live encrypted in the database.

**Why:** no middleman; GitHub's own visibility model enforces owner-scoping; setup is
click-through with no manual webhook configuration.

**Rejected:** a shared public app (cannot route webhooks to per-user workers; strangers could
install it); manual app creation (strictly worse than the manifest flow).

## D-006: Review run engine — per-run Durable Object

**Date:** 2026-10-02

**Decision:** Each review run is coordinated by a per-run Durable Object. The webhook handler
acknowledges fast and kicks the run; the Durable Object executes phases through alarms —
load run context, run each reviewer (parallel provider calls), consolidate, post one review,
record the run — persisting state between phases so runs survive restarts and retry with
backoff. Alarm segments get 15 minutes of wall time; I/O waiting does not count toward CPU.

**Why:** Durable Objects are available on the free plan (100k requests/day, 13k GB-s/day,
SQLite-backed) and inherit the plan's per-invocation CPU limits (free 10 ms, paid 30 s) — the
same ceiling as every other option, without paid-only products. Review processing is kept
I/O-bound and chunked to fit the free tier (see `docs/architecture.md` boundaries).

**Rejected:** Cloudflare Workflows (effectively paid-only: free tier caps compute at 10 ms per
step); Queues (paid-only, and fan-out is small); cron polling (minutes of latency); running
reviews inside the webhook request (no time budget, GitHub expects a fast response).

## D-007: Branch protections and the release token

**Date:** 2026-10-02

**Decision:** Classic branch protection is enabled on `dev` and `main`: pull requests required
(0 approvals — self-merge allowed), force pushes and deletions blocked, admins not enforced.
The release workflow is the only direct push to `main`; it authenticates with a `RELEASE_TOKEN`
repository secret (a repo-admin token with `contents: write`) and fails with setup instructions
when the secret is missing.

**Why:** on user-owned (personal) repositories, GitHub does not allow granting the GitHub Actions
integration bypass on branch protections — verified on 2026-10-02: classic bypass allowances
error with "Only organization repositories can have users and team restrictions", and rulesets
reject the Actions actor with "must be part of the ruleset source or owner organization". The
standard workaround is an admin token, which bypasses classic protection when
`enforce_admins` is off.

**Manual step:** create the token and set the secret before the first release (see
`docs/development.md`, Releases and deploys).

## D-008: First-run setup protection — deploy-time setup code

**Date:** 2026-10-02

**Decision:** A fresh instance cannot be claimed until the owner sets a random `SETUP_CODE`
Worker secret at deploy time. The setup wizard requires the code to complete the one-time
claim, and claiming closes the wizard once an owner exists. The code lives only as a Worker
secret — never in D1, never logged.

**Why:** protects the window between deploy and claim without extra services or Zero Trust
setup, and it fits the existing manual deploy flow, which already sets `ENCRYPTION_KEY`.
Confirmed by the user in chat on 2026-10-02.

**Rejected:** first-visitor claim (a deploy-to-claim race; it does not actually prevent a
stranger); Cloudflare Access for Workers (strong, but adds Zero Trust setup, blocks webhook
delivery while enabled, and needs relaxing after the claim).

## D-009: Comment volume caps

**Date:** 2026-10-02

**Decision:** A run posts at most 10 inline comments per reviewer and 25 inline comments in
total. Overflow, and findings without a file/line, land in the consolidated review summary,
attributed per reviewer with `file:line` references.

**Why:** keeps reviews actionable instead of noisy and bounds GitHub API calls per run.
Confirmed by the user in chat on 2026-10-02.

**Rejected:** 20 per reviewer / 50 per run (noisier, heavier); uncapped — every finding inline
(noisy and unbounded).

## D-010: Diff size budget for review context

**Date:** 2026-10-02

**Decision:** The context builder caps the diff sent per reviewer at 200 KB in total and 32 KB
per file; lockfiles, generated files, and binaries are skipped; truncation is stated in the
review. v1 ships these as fixed defaults — not per-instance configuration.

**Why:** keeps prompts within common model context windows and processing within free-tier CPU
budgets (see `docs/architecture.md`, free-tier posture). Confirmed by the user in chat on
2026-10-02.

**Rejected:** 64 KB total / 16 KB per file (over-truncates large PRs); no cap (token overflows,
CPU spikes).

## D-011: Pull-request checks for stacked slices

**Date:** 2026-10-02

**Decision:** The CI workflow runs `npm run check` on every pull request, whatever its base
branch; pushes are still checked only on `dev`. This supersedes the pull-request trigger detail
in D-001. Phase-2 work lands as stacked pull requests — each slice targets the previous slice's
branch — and every layer must show the check.

**Why:** the user asked for the stacked-PR workflow on 2026-10-02; with the old
`branches: [dev, main]` filter on `pull_request`, layers targeting each other showed no checks
at all.

**Rejected:** keeping the filter and checking only after a layer retargets to `dev` (feedback
arrives too late); checking pushes everywhere too (no benefit).

## D-012: Dashboard access — installation-access gate

**Date:** 2026-10-02

**Decision:** Dashboard access requires a GitHub OAuth sign-in whose token can see the
instance's installation (`GET /user/installations`); the first access-gated user claims the
instance. No separate allowlist is built in v1. Implementation lands in phase-2 slice 2.

**Why:** GitHub's rules for private apps already bound who may authorize the app; following
installation access covers the owner and the org members GitHub grants access. Recommended in
`docs/design.md` and accepted by the user in chat on 2026-10-02.

**Rejected:** an allowlist UI (extra state and surface for v1); an open dashboard.

## D-013: Publishing — one COMMENT review per run

**Date:** 2026-10-02

**Decision:** A run publishes exactly one GitHub review, posted with `event: COMMENT` — never
`REQUEST_CHANGES` in v1 — subject to the D-009 caps; findings that cannot attach to a line land
in the summary. Implementation lands in phase-2 slice 4.

**Why:** the bot should not block merges; `REQUEST_CHANGES` would wherever branch protection
counts reviews. Recommended in `docs/design.md` and accepted by the user in chat on 2026-10-02.

**Rejected:** `REQUEST_CHANGES` (blocks merges); posting findings as individual comments (loses
the one-review contract and the caps).

## D-014: Outbound request mocking — MSW via `@msw/cloudflare`

**Date:** 2026-10-02

**Decision:** Tests mock outbound HTTP (GitHub now, model providers later) with Mock Service
Worker: `msw` and `@msw/cloudflare` as product dev dependencies, a shared `setupNetwork()`
module, and per-test handlers via `network.use()`. Versions resolved live on 2026-10-02:
`@msw/cloudflare` 0.2.0 (peers `msw >= 3`; current `msw` 3.0.1 satisfies it). The dependencies
land with phase-2 slice 2a.

**Why:** it is the Workers Vitest plugin's supported path for outbound mocking — the old
`fetchMock` export is gone and the plugin's guide directs to `@msw/cloudflare`; per-test
handlers stay declarative, and interception covers worker and Durable Object code without
production-code seams.

**Rejected:** `vi.stubGlobal("fetch")` (Workers globals are not stubbable); fetch-injection
plumbing through routes and the run engine (production code shaped by tests); a config-level
`miniflare.outboundService` mock (no per-test control).
