# Decisions

Append-only log of settled decisions. New entries get the next number, a date, and a sentence of
context. If a decision is reversed, add a new entry that supersedes the old one — never edit
history. The agent records decisions here **before** implementing them (see `AGENTS.md`, rule 2).

    (see D-006). Worker types generated by `wrangler types` into a committed

Vercel/Next.js (short-lived functions cannot run review jobs); Cloudflare Agents SDK
(WebSocket/stateful-agent shaped — a plain Durable Object state machine is smaller); Cloudflare
Workflows (effectively paid-only — free tier caps step compute at 10 ms; see D-006); Drizzle ORM
(raw SQL plus `wrangler d1 migrations` is enough for this schema); `@cloudflare/workers-types`
(superseded by `wrangler types`); TypeScript 7.0.2 and Vitest 5.0.3 (ecosystem lag, noted above).

**Confirmed by the user in chat on 2026-10-02** (name, runtime, dashboard surface, execution
model, and the post-pivot shape).

## D-002: Branching and automated releases

**Date:** 2026-09-26

**Decision:** `dev` is the default integration branch. Agent changes use feature branches and
pull requests targeting `dev`; releases flow from `dev` to `main`. Release-related workflows run
only after changes merge to `main`. A release PR must carry exactly one of
`release:patch`, `release:minor`, or `release:major`; the release automation applies that bump to
the chosen stack's version source, creates a matching `v<version>` tag, and publishes a GitHub
release. A merge without a release label does not publish a release. `dev` carries unreleased
work between releases and may match `main` immediately after one. Product/site deployment remains
manual. Implemented on 2026-10-02 as `.github/workflows/release.yml` + `scripts/release.mjs`
(version source: root `package.json` / `package-lock.json` / `CHANGELOG.md`).

## D-003: Agent operating model

**Date:** 2026-09-26

**Decision:** The primary agent acts as senior architect and owns requirements analysis,
architecture, documentation, code generation, integration, testing, and final verification.
Subagents are optional and restricted to one sequential, read-only discovery or evidence-gathering

## D-004: Distribution model — self-hosted, single-tenant

**Date:** 2026-10-02

**Decision:** Jury Forge ships as a self-hosted, single-tenant deployment. Each user deploys
their own instance (Worker + D1 + their own private GitHub App) into their own Cloudflare
account; the project operates no central service and holds no user data. Default cost posture is
Cloudflare's free plan, with Workers Paid ($5/month, the owner's own account) documented as
optional headroom for CPU on very large PRs. The promo site is static and deploys separately.

**Why:** the user's directive — code, credentials, and model spend stay in the owner's account;
no platform to operate or pay for; single-tenant removes multi-tenant auth and data modeling
entirely.

**Rejected:** a shared hosted app (platform cost + custody of user credentials and code);
"install a shared app, then it provisions your worker" (a GitHub App has exactly one webhook
URL, and provisioning into someone's Cloudflare account would require a central service —
exactly what this model avoids).

## D-005: Per-instance private GitHub App via the manifest flow

**Date:** 2026-10-02

**Decision:** The setup wizard registers a **private** GitHub App owned by the user's personal
account or an organization they administer, using GitHub's App Manifest flow. The manifest
prefills the webhook URL, OAuth callback, permissions, and events from the instance's own URL
(`public: false`). Private apps are installable only on the owning account, and only the owner
(personal) or members of the owning organization can authorize them. The app's runtime-generated
credentials (app id, private key, webhook secret, client secret) and all BYOK provider keys are
encrypted with AES-256-GCM (WebCrypto) and stored in the instance's D1, with the master key held
as a Worker secret — Workers secrets cannot be written at runtime, so runtime-created credentials
must live encrypted in the database.

**Why:** no middleman; GitHub's own visibility model enforces owner-scoping; setup is
click-through with no manual webhook configuration.

**Rejected:** a shared public app (cannot route webhooks to per-user workers; strangers could
install it); manual app creation (strictly worse than the manifest flow).

## D-006: Review run engine — per-run Durable Object

**Date:** 2026-10-02

**Decision:** Each review run is coordinated by a per-run Durable Object. The webhook handler
acknowledges fast and kicks the run; the Durable Object executes phases through alarms —
load run context, run each reviewer (parallel provider calls), consolidate, post one review,
record the run — persisting state between phases so runs survive restarts and retry with
backoff. Alarm segments get 15 minutes of wall time; I/O waiting does not count toward CPU.

**Why:** Durable Objects are available on the free plan (100k requests/day, 13k GB-s/day,
SQLite-backed) and inherit the plan's per-invocation CPU limits (free 10 ms, paid 30 s) — the
same ceiling as every other option, without paid-only products. Review processing is kept
I/O-bound and chunked to fit the free tier (see `docs/architecture.md` boundaries).

**Rejected:** Cloudflare Workflows (effectively paid-only: free tier caps compute at 10 ms per
step); Queues (paid-only, and fan-out is small); cron polling (minutes of latency); running
reviews inside the webhook request (no time budget, GitHub expects a fast response).

## D-007: Branch protections and the release token

**Date:** 2026-10-02

**Decision:** Classic branch protection is enabled on `dev` and `main`: pull requests required
(0 approvals — self-merge allowed), force pushes and deletions blocked, admins not enforced.
The release workflow is the only direct push to `main`; it authenticates with a `RELEASE_TOKEN`
repository secret (a repo-admin token with `contents: write`) and fails with setup instructions
when the secret is missing.

**Why:** on user-owned (personal) repositories, GitHub does not allow granting the GitHub Actions
integration bypass on branch protections — verified on 2026-10-02: classic bypass allowances
error with "Only organization repositories can have users and team restrictions", and rulesets
reject the Actions actor with "must be part of the ruleset source or owner organization". The
standard workaround is an admin token, which bypasses classic protection when
`enforce_admins` is off.

**Manual step:** create the token and set the secret before the first release (see
`docs/development.md`, Releases and deploys).

## D-008: First-run setup protection — deploy-time setup code

**Date:** 2026-10-02

**Decision:** A fresh instance cannot be claimed until the owner sets a random `SETUP_CODE`
Worker secret at deploy time. The setup wizard requires the code to complete the one-time
claim, and claiming closes the wizard once an owner exists. The code lives only as a Worker
secret — never in D1, never logged.

**Why:** protects the window between deploy and claim without extra services or Zero Trust
setup, and it fits the existing manual deploy flow, which already sets `ENCRYPTION_KEY`.
Confirmed by the user in chat on 2026-10-02.

**Rejected:** first-visitor claim (a deploy-to-claim race; it does not actually prevent a
stranger); Cloudflare Access for Workers (strong, but adds Zero Trust setup, blocks webhook
delivery while enabled, and needs relaxing after the claim).

## D-009: Comment volume caps

**Date:** 2026-10-02

**Decision:** A run posts at most 10 inline comments per reviewer and 25 inline comments in
total. Overflow, and findings without a file/line, land in the consolidated review summary,
attributed per reviewer with `file:line` references.

**Why:** keeps reviews actionable instead of noisy and bounds GitHub API calls per run.
Confirmed by the user in chat on 2026-10-02.

**Rejected:** 20 per reviewer / 50 per run (noisier, heavier); uncapped — every finding inline
(noisy and unbounded).

## D-010: Diff size budget for review context

**Date:** 2026-10-02

**Decision:** The context builder caps the diff sent per reviewer at 200 KB in total and 32 KB
per file; lockfiles, generated files, and binaries are skipped; truncation is stated in the
review. v1 ships these as fixed defaults — not per-instance configuration.

**Why:** keeps prompts within common model context windows and processing within free-tier CPU
budgets (see `docs/architecture.md`, free-tier posture). Confirmed by the user in chat on
2026-10-02.

**Rejected:** 64 KB total / 16 KB per file (over-truncates large PRs); no cap (token overflows,
CPU spikes).

**Date:** 2026-10-02

**Decision:** The CI workflow runs `npm run check` on every pull request, whatever its base
branch; pushes are still checked only on `dev`. This supersedes the pull-request trigger detail

**Why:** the user asked for the stacked-PR workflow on 2026-10-02; with the old

**Rejected:** keeping the filter and checking only after a layer retargets to `dev` (feedback

## D-012: Dashboard access — installation-access gate

**Date:** 2026-10-02

**Decision:** Dashboard access requires a GitHub OAuth sign-in whose token can see the
instance's installation (`GET /user/installations`); the first access-gated user claims the
instance. No separate allowlist is built in v1. Implementation lands in phase-2 slice 2.

**Why:** GitHub's rules for private apps already bound who may authorize the app; following
installation access covers the owner and the org members GitHub grants access. Recommended in
`docs/design.md` and accepted by the user in chat on 2026-10-02.

**Rejected:** an allowlist UI (extra state and surface for v1); an open dashboard.

## D-013: Publishing — one COMMENT review per run

**Date:** 2026-10-02

**Decision:** A run publishes exactly one GitHub review, posted with `event: COMMENT` — never
`REQUEST_CHANGES` in v1 — subject to the D-009 caps; findings that cannot attach to a line land
in the summary. Implementation lands in phase-2 slice 4.

**Why:** the bot should not block merges; `REQUEST_CHANGES` would wherever branch protection
counts reviews. Recommended in `docs/design.md` and accepted by the user in chat on 2026-10-02.

**Rejected:** `REQUEST_CHANGES` (blocks merges); posting findings as individual comments (loses
the one-review contract and the caps).

## D-016: Run activation — repository and reviewer selection

**Date:** 2026-10-07

**Decision:** A webhook-triggered run proceeds only when the repository is present and enabled in
`repositories`; otherwise it finishes `skipped`. Reviewer selection is opt-out: every enabled
reviewer applies to every enabled repository unless a `reviewer_repositories` row for that pair
sets `enabled = 0`. Runs with no applicable reviewers finish `skipped`.

**Why:** the dashboard's per-repo reviewer toggles (slice 5) default to on, and `repositories` is
the opt-in surface for which repositories Jury Forge reviews at all; the engine never reviews a
repository nobody enabled.

**Rejected:** double opt-in (each reviewer explicitly enabled per repo — noisy for the common
case); auto-registering repositories on webhook activity (reviews without consent).

## D-018: Run hygiene — superseded-run skip, review minimization, priority file order

**Date:** 2026-10-07 (implements roadmap items 1, 2, 4 from D-017)

**Decision:** (1) At its config step, a run finishes `skipped` when a newer run exists for the
same repository and PR (`created_at`, then id, ordering) — covering supersession on rapid pushes
and duplicate deliveries of the same head SHA; the newest run wins. In-flight runs are not
cancelled. (2) After posting, the app's previous reviews on the PR are minimized best-effort via
GraphQL `minimizeComment` (`OUTDATED` classifier); minimization failures never affect the run.
(3) Under the D-010 budget, files are sent in priority order — added/changed source first, docs
and renames trail — so truncation drops the least valuable diffs.

**Why:** rapid pushes otherwise burn provider spend N times and stack N reviews on the PR, and
the context budget should truncate the least valuable diffs, not the first ones the API returned.

**Rejected:** cancelling in-flight runs (by the time a newer push arrives the old work is mostly
spent; the newest queued run wins instead); deleting previous reviews (destructive, loses
history); raw API order for files (drops high-signal diffs first).

## D-020: Slice 7 — resolution tracking and output contract v2

**Date:** 2026-10-17 (implements roadmap items 3 and 6 from D-017)

**Decision:** (1) **Resolution tracking.** When a run starts, the newest earlier run for the same
repository and pull request that recorded findings supplies those findings to the new run: each
reviewer's prompt gains a "previously reported findings" section carrying that reviewer's own
earlier findings, and the review summary gains **Resolved / Still present / New** buckets. The
buckets are computed deterministically by comparing the earlier run's findings with the current
run's — a finding is keyed by `file`, `line` (or `file` alone when the finding is file-level),
and case-folded `title`; the model is never asked to grade its own previous output. Reported
earlier and absent now → `resolved`; present in both → `still present`; absent earlier → `new`.
"Resolved" means only _this run did not report it again_, and the summary says so. The buckets
appear when an earlier run with findings exists for the PR.

(2) **Output contract v2.** The prompt's JSON contract gains an optional per-reviewer `summary`
(≤500 characters; stored with the reviewer's outcome and shown in run detail) and a per-finding
`startLine` for multi-line comments. `startLine` is used only when it precedes `line` and both
lines are commentable in the diff's right side — then the inline comment carries GitHub's
`start_line` with `start_side: RIGHT`; otherwise `startLine` is dropped and the finding posts as
a single-line comment. Oversized summaries are truncated like titles and bodies. Provider token
`usage` is read from both flavors' response envelopes, normalized to
`{ promptTokens, completionTokens, totalTokens }`, and stored per reviewer in run detail
(`run_reviewers.usage_json`); a provider that reports no usage stores nothing and never fails the
reviewer for it.

**Why:** a reviewer that never sees what it flagged last time repeats itself or contradicts
itself, and the reviewer — not the model — is the right place to decide what stopped being
reported; the contract changes are the two pieces the phase-2 design flagged as deferred v1
cutbacks (`summary`, multi-line findings) plus the usage numbers needed before anyone tunes a
provider budget.

**Rejected:** asking the reviewer model to classify its own previous findings (unverifiable,
provider-dependent, and it would make the buckets a self-assessment rather than a diff); a
resolution table keyed by stable finding ids (the contract has no ids, and a deterministic key is
sufficient for a single-instance tool); keeping the previous-run context out of the prompt and
computing buckets only in the summary (the prompt section is what stops the redundant re-report;
the buckets are the receipt for it); treating a missing `usage` envelope as a reviewer failure
(the envelope is optional and provider-specific); `REQUEST_CHANGES`-style pressure from resolved
counts (blocking is item 11's explicit opt-in, D-013 otherwise stands).

## D-021: Slice 8 — instance settings and optional blocking mode

**Date:** 2026-10-17 (implements roadmap items 5 and 11 from D-017)

**Decision:** (1) **Instance settings.** A new `instance_settings` key/value table (`key`,
`value`, `updated_at`) holds the numbers phase 2 fixed in code, with the current values as
defaults: `inlineCommentsPerReviewer` (1–50, default 10), `inlineCommentsPerRun` (1–100, default
25), `contextTotalBytes` (20,000–1,000,000, default 200,000), `contextFileBytes` (4,000–200,000,
default 32,000), `descriptionLimit` (500–20,000, default 4,096), plus the blocking pair below.
`worker/lib/settings.ts` owns the spec (parser, bounds, default per key); `loadSettings()` returns
effective settings and falls back to a key's default whenever the stored value is missing or
invalid, so a hand-edited row can never break a run. `GET /api/settings` returns
`{ settings, defaults }`; `PATCH /api/settings` accepts a partial object, rejects unknown keys and
out-of-range values with 400, and returns the same shape. The dashboard gains a Settings screen
(the "Advanced" section) with the current values as defaults, per-field reset, and save. The run
engine reads the settings in its `config` step and uses them for the context budget, the
description cap, the inline comment caps, and the review event.

(2) **Optional blocking mode** (item 11). `blockingMode` (boolean, default **false**) and
`blockingErrorThreshold` (1–50, default 1) select the review event: with blocking off — the
default, and D-013's posture — every run posts `event: COMMENT`. With it on, a run whose findings
include at least `blockingErrorThreshold` findings of severity `error` posts
`event: REQUEST_CHANGES`; any other run still posts `COMMENT`. The review body's notes state which
event was used, and when blocking was on without reaching the threshold.

**Why:** D-009/D-010's numbers were v1 defaults, not laws — a large diff or a chatty reviewer
should be tunable from the dashboard instead of by editing the Worker and redeploying; and
blocking is the one behavior an owner plausibly wants from a review bot on their own repository,
so it ships as a switch that is off until the owner flips it, keeping the documented D-013
posture for every instance that never touches it.

**Rejected:** env-var or `wrangler.jsonc` configuration for the numbers (a redeploy per tweak,
and it puts product behavior in deploy config); per-repository settings in this slice (the demand
is per-instance; per-repo tuning can be a later decision with its own table); turning blocking on
by default or inferring it from severity counts (it would silently change merge behavior for
existing instances — D-013 stands as the default); blocking on _any_ error finding regardless of
threshold (noisy for reviewers that flag errors liberally — the threshold is the escape hatch);
a separate `blocking` column on `runs` (the posted `review_url` and the summary's note already
record what happened).

## D-022: Slice 9 — repository instructions in prompts, opt-in

**Date:** 2026-10-17 (implements roadmap item 10 from D-017)

**Decision:** With `repoInstructions` (boolean, default **false**) on, a run reads the
repository's `AGENTS.md` and `CONTRIBUTING.md` at the pull request's head SHA — through the
installation token, raw media type, in that order — and includes bounded excerpts in the user
prompt of every reviewer that run. The excerpt budget `repoInstructionsMaxBytes` (int
1,000–50,000, default 8,000) applies across both files: the first file that fits is included in
full, the file that crosses the budget is truncated there, and any file past the budget is
omitted; the block names what was truncated or skipped. The block is introduced as repository
conventions that inform the review, and the prompt states that the reviewer's own instructions
and rules take precedence over it. A 404 (no such file) or any fetch failure skips that file and
never fails the run — the setting adds at most two subrequests per run, and the excerpts are
re-read for every run rather than cached.

**Why:** a repository's own conventions live in these files, and a reviewer that never sees them
flags style the project has already settled; grounding the reviewer in the PR's own revision of
those files is the smallest change that makes the reviews fit the repository — and keeping it
opt-in respects that it changes what the model sees on every run.

**Rejected:** on by default (an unasked-for file read plus up to 8 KB of prompt per reviewer on
every run); reading the files from the default branch instead of the PR's head SHA (the revision
under review is the one whose conventions apply, and a PR that rewrites `AGENTS.md` should be
reviewed against its own text); sending whole files unbounded (one large `AGENTS.md` would
consume the context budget); putting the block in the system prompt (it is context, not the
reviewer's identity — and the system prompt carries the output contract); a dashboard field for
per-repository instruction text (the repository already carries this; per-repo overrides stay a
later decision); caching the excerpts in D1 (runs are rare, the files are small, and a cache is
state to invalidate for no measured win).

## D-023: Slice 10 — credential key rotation and the audit trail

**Date:** 2026-10-17 (implements roadmap items 7 and 12 from D-017)

**Decision:** (1) **Key rotation** (item 7). Ciphertexts become versioned —
`v2.<keyVersion>.<iv>.<ciphertext>` — and the legacy `v1.<iv>.<ciphertext>` form stays readable.
`worker/lib/crypto.ts` exposes a key ring built from the environment: `ENCRYPTION_KEY` plus
`ENCRYPTION_KEY_VERSION` (default `1`), and optionally `ENCRYPTION_KEY_PREVIOUS` plus
`ENCRYPTION_KEY_PREVIOUS_VERSION` (default `0`). Writes always use the current key and stamp its
version; reads pick the key by version (`v2` with an unknown version fails; a legacy `v1` value is
tried with the current key, then the previous one). Rotation needs no re-entry: a reviewer's API
key is **lazily re-encrypted on its next write** — the same plaintext re-wrapped with the current
key, in the same `PATCH` — and every credential write (app registration, reviewer create/update)
stamps the current version. GitHub App credentials have no partial-update path, so they are
re-encrypted only by re-running the app registration; the previous key stays configured until then.
The operator procedure lives in `docs/development.md`.

(2) **Audit trail** (item 12). A new `activity_log` table (`at`, `actor`, `action`, `target`,
`detail`) records **sign-ins and sign-outs, setting changes, reviewer create/update/delete
(including whether the API key was set, cleared, or re-encrypted by rotation), repository and
per-repo reviewer toggles, run kicks, and credential rotations**. Writes go through
`worker/lib/activity.ts`'s `recordActivity()`, which is best-effort — a failed insert is logged and
swallowed so it can never fail the request — and `GET /api/activity` returns the newest first with
a keyset cursor (`at`, then `id`) and prunes entries older than 90 days opportunistically. The
dashboard gains an `/activity` screen listing time, actor, action, target and detail with the same
"load more" pattern as runs.

**Why:** D-005's "rotate by re-entering every credential" was acceptable only while there were no
instances; a versioned ring makes rotation an environment change with no credential re-entry, and
it keeps the AES-256-GCM secrets write-only from the API's perspective. And once a self-hosted
instance has settings, credentials and toggles, "who changed this, when" should be answerable from
the dashboard rather than by reading D1 — a single-instance tool's owner is the whole audience for
an audit trail, and 90 days of it is enough.

**Rejected:** a full key-derivation/labelled-keys vault in D1 (the instance's keys live in Worker
secrets by design — D-005 — and a second store of key material would be a new blast radius);
eager re-encryption of every row on rotation (a migration-shaped background job for a single
instance; lazy re-wrapping plus the previous key reaches the same end state with no window where
the Worker cannot read); versioning without a previous key (it would make every rotation a
credential re-entry, i.e. no rotation); dropping support for `v1` ciphertexts (existing instances
would need a manual migration); an activity export/download endpoint (a reading surface is what was
asked for; the table is one `SELECT` away for anyone who wants more); recording request-level noise
like every page view or failed login (the trail is for state changes, not traffic); an unbounded
trail (a single instance accumulates rows forever for no benefit — 90 days, pruned on read).
