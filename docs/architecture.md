# Architecture

## Shape

Jury Forge is a self-hosted, single-tenant GitHub App. One repository holds:

- `product/` — the deployable: a single Cloudflare Worker that receives GitHub webhooks, serves
  the dashboard API and the React dashboard itself (static assets), and orchestrates review
  runs; plus one Cloudflare D1 database.
- `site/` — the static promo site (Astro). It deploys independently, imports only `shared/`
  brand constants, and never touches the product's runtime.
- `shared/` — brand constants and API contract types, consumed as TypeScript source.

Each instance is one Cloudflare account, one Worker, one D1 database, and its own private GitHub
App. There is no central service — nothing runs anywhere but the owner's account.

The detailed phase-2 design — data model, API surface, setup and run flows — lives in
`docs/design.md`.

## Components

| Piece                | Where                                                  | Responsibility                                                                                                                                  |
| -------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker               | `product/worker/`                                      | Hono app: `/api/*` (dashboard API), webhook receiver (signature-verified), GitHub OAuth + setup wizard (phase 2); kicks per-run Durable Objects |
| Dashboard            | `product/src/`                                         | React SPA, served by the Worker through static assets (SPA fallback; `run_worker_first: ["/api/*"]`)                                            |
| Run engine (phase 2) | `product/worker/` (Durable Object)                     | Per-run state machine: context fetch, reviewer execution (parallel provider calls), consolidation, one review posted, retries with backoff      |
| Database             | D1 (binding `DB`)                                      | `instance_meta` today; reviewers, encrypted credentials, repositories, runs land in phase 2. SQL migrations in `product/migrations/`            |
| Worker types         | `product/worker-configuration.d.ts`                    | Generated by `wrangler types`; committed. Regenerate after changing `product/wrangler.jsonc`                                                    |
| Promo site           | `site/`                                                | Static landing page; deploy target configured in `site/wrangler.jsonc` (assets only)                                                            |
| CI                   | `.github/workflows/ci.yml`                             | `npm run check` on PRs to `dev`/`main` and pushes to `dev`                                                                                      |
| Release              | `.github/workflows/release.yml`, `scripts/release.mjs` | Label-driven version bump, tag, and GitHub release on merges to `main`                                                                          |

## Data flow

1. **Setup** — the owner deploys the Worker, opens the dashboard, and the wizard registers a
   private GitHub App through GitHub's manifest flow (webhook URL and OAuth callback pointing at
   the instance itself). The owner installs the app, claims the instance (the one-time claim
   requires the deploy-time `SETUP_CODE` secret, D-008), and configures reviewers. All generated
   credentials and provider keys are encrypted into D1 (D-005).
2. **Review** — GitHub delivers a pull request event to the instance's webhook URL. The Worker
   verifies the HMAC signature, de-duplicates the delivery, and kicks a per-run Durable Object,
   which fetches PR context, runs the enabled reviewers against their configured providers
   (OpenAI-compatible or Anthropic-compatible, any base URL), consolidates findings, and posts
   one review back to the pull request. The run is recorded in D1.
3. **Dashboard** — the browser talks to `/api/*` on the same origin; sessions come from GitHub
   OAuth through the instance's own app.

What leaves the owner's account: requests to GitHub and to the model providers the owner
configured. Nothing else.

## Boundaries and invariants

- **No central service.** The project ships code and a static site; it never receives user code,
  events, or credentials.
- **Secrets** live only in the owner's account: encrypted at rest with AES-256-GCM (WebCrypto),
  master key held as a Worker secret; never logged; decrypted only in memory to call GitHub or
  the configured provider.
- **Private apps are owner-scoped** (GitHub enforces installability), and dashboard authorization
  is limited to the owner or owning-organization members.
- **Free-tier posture.** Worker and Durable Object invocations are capped at 10 ms CPU on the
  free plan (30 s on Workers Paid). Review processing must stay I/O-bound and chunked: prefer raw
  diff text over large JSON payloads, cap diff size (D-010), and split work across alarm segments.
- **Deployments are manual**, always to the owner's own account, and only when asked.

## Branch and release flow

- `dev` is the default branch and the integration target. Agent work happens on feature branches
  and reaches `dev` through pull requests.
- A release is proposed by a pull request from `dev` to `main` carrying exactly one
  `release:patch`, `release:minor`, or `release:major` label.
- On merge to `main`, the release workflow (only there) bumps the root `package.json` version
  (version source; `package-lock.json` and `CHANGELOG.md` move with it), creates the matching
  `v<version>` tag, and publishes a GitHub release. A merge without a release label publishes
  nothing.
- Because `main` is protected and personal repositories cannot grant the GitHub Actions
  integration a bypass (D-007), the workflow pushes with the `RELEASE_TOKEN` secret — a
  repo-admin token with `contents: write`. Without the secret, the release job fails with
  instructions and nothing is published.
- Deployments of the product and the site stay manual; see the `ship-release` skill.

## Required repository settings (configured 2026-10-02)

- Default branch: `dev`.
- Labels: `release:patch`, `release:minor`, `release:major`.
- Branch protection on `dev` and `main`: pull requests required (0 approvals), no force pushes,
  no deletions, admins not enforced, and the `check` CI status required.
- Secret: `RELEASE_TOKEN` (repo-admin token with `contents: write`) — required before the first
  release.
