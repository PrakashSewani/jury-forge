# ADR-0021: Runtime-configured public origin

- Status: proposed
- Date: 2026-11-15
- Owners: architecture + operations + security
- Supersedes: the "set `PUBLIC_URL` in `.env` before first start" assumption in the ops draft
- Revisit trigger: a deployment model that cannot reach the instance before DNS exists, or support
  for sub-path hosting.

## Context

GitHub needs a stable public origin **before** an App can be created: the manifest records the
webhook URL, the OAuth callback, and the redirect URL. The ops draft required the operator to edit
`PUBLIC_URL` in `.env` and restart, which means the domain is a host-level precondition rather than
a setup step. That is worse than it sounds:

- The operator has to leave the product to configure it, with no validation that DNS, TLS, or
  GitHub reachability will work.
- A typo is discovered only when the GitHub App is created and webhooks never arrive.
- Changing a domain later has no defined flow, yet small teams do move instances.
- It makes the setup UI unable to show the exact URLs GitHub will call, which is the one thing the
  operator must verify.

The owner asked (2026-11-15) for the domain to be **dynamic / part of first launch, before the
GitHub App step** — e.g. `jury.prakashsewani.com`.

## Options

1. **Env-only (`PUBLIC_URL` in `.env`).** Simple, immutable, no DB setting. Bad first-run UX and no
   change flow. Current draft.
2. **Setup-configured, stored in the database, env can override.** The domain is a first-class
   instance setting; the UI validates DNS/TLS before the App step; env freezes it for
   pre-provisioned installs.
3. **Derive from the request `Host`.** Zero config, but trusts a user-controlled header for OAuth
   redirects and webhook URLs — host-header injection. Rejected.
4. **Reverse-proxy-managed origin (operator writes the Caddyfile).** Works, but keeps the domain out
   of the product and out of the audit trail.

## Decision

Option 2. The public origin is an **instance setting**, written once during setup and changeable by
an owner with re-authentication.

- **Precedence:** `PUBLIC_URL` env (if set) is authoritative and **locks** the origin (air-gapped,
  pre-provisioned, or operator-managed config). Otherwise `instance.public_url` in Postgres.
  Otherwise the instance is unconfigured and only bootstrap is available.
- **Bootstrap access is never public.** Before an origin exists, setup is served on a loopback
  listener (`SETUP_BIND`, default `127.0.0.1:8080`) protected by the bootstrap token. The operator
  uses SSH port-forwarding, `curl` on the host, or `jury-forge setup domain <host>`.
- **One origin, no path.** `https://<host>` only; no sub-path (`/jury-forge` is unsupported).
- **TLS is on-demand.** Caddy serves `:443` with `tls { on_demand }` and an `ask` endpoint that
  authorizes **only** the configured origin; issuance is rate-limited (Caddy interval/burst plus an
  app-side limit). No proxy config is generated by the app and no reload is needed.
- **The origin is enforced, not inferred.** Requests whose `Host` is not the configured origin get
  `421 Misdirected Request` (or `404` on unknown hosts), except the loopback bootstrap listener.
  OAuth `redirect_uri`, CSRF origin checks, and webhook URLs are all built from the stored origin;
  the `Host` header is never trusted as a source of truth.
- **Changing the origin is a first-class flow.** Owner + re-auth; validate the new origin; write and
  audit `origin.changed`; update the GitHub App's hook, callback, and redirect URLs via `PATCH /app`
  (the App updates its own settings with a JWT); invalidate sessions (host-only cookies already
  die); keep a banner until a webhook self-test succeeds against the new origin.

## Consequences

**Easier:** the domain is set and validated in one place, the UI can show exactly which URLs GitHub
will call, pre-provisioned installs can still pin it, and a move is a supported action.

**Harder:** one more instance setting and validation path; on-demand TLS needs an `ask` endpoint and
careful rate limits; the proxy must be configured once with on-demand TLS rather than a fixed site
address; origin changes touch GitHub App settings and sessions.

**Constraints:** bootstrap is loopback-only; no request header can define the origin; one origin per
instance; sub-path hosting is out for v1.

## Security and operations

- Host-header injection is the primary risk this closes: without a stored origin, an attacker can
  shape OAuth redirects and password-reset style links with `Host`.
- Bootstrap listener binds to loopback by default; exposing it requires an explicit env change and
  is logged as a warning by `doctor`. The bootstrap token remains single-use, expiring, rate-limited.
- The TLS `ask` endpoint is on the internal network, answers only "is this the configured domain?",
  and is rate-limited; it never issues a certificate for any other name.
- On-demand issuance is capped per domain and per instance to avoid ACME rate-limit abuse.
- Origin changes, failed validations, and `PATCH /app` calls are audited with actor and old/new value.
- `.jury-forge.yml` and other repo config cannot change the origin.

## Follow-ups

- Spike: Caddy `on_demand_tls` `ask` behaviour when the app is not yet reachable (cold start) and
  when the origin changes; confirm no certificate is issued for an unconfigured host.
- Decide whether a wildcard certificate is worth offering for air-gapped/proxied installs.
- Confirm the exact GitHub `PATCH /app` fields required to move hook/callback/redirect URLs.
